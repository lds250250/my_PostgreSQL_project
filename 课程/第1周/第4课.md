# 第 4 课：数据目录与 WAL

> **本课对应**：`README.md` 第 1 周 Day 4
> **前置**：`课程/第1周/第3课.md`
> **状态**：✅ 已完成
> **读完本课能做出什么**：说出"你的数据到底存在哪"，并知道哪几个文件动不得
> **本课产出的长期文件**：无

**本课的点**

- **重点**：`base/` 里一个数字目录 = 一个库；`pg_wal/` 是崩溃恢复的安全网
- **难点**：为什么一个库不是"一个文件"，而是"一堆文件"
- **普通点**：数据目录里都有什么；哪几个能动、哪几个不能

**今天唯一要形成的模型：**

> **数据库 = 磁盘上一个文件夹 + 一个正在运行的进程。
> 文件夹里每个库占一个子目录；所有库共用一条 WAL 流水账。
> 文件在，数据就在 —— 进程停不停不影响。**

---

## 一、今天解决什么问题

**你有没有想过：你把数据交给数据库，它到底存到哪去了？**

你敲 `INSERT` 之后，数据变成什么了？是一个 `.db` 文件吗？像 SQLite 那样？
**如果哪天不小心删了某个文件，数据是不是就没了？哪些能删、哪些一删库就废？**

**今天学的就是这个 —— 它叫数据目录（`data directory`）和预写日志（`pg_wal`）。**

**一句话说：数据库就是硬盘上的一个文件夹。每个库在这个文件夹里占一个小目录，所有库共用一条"流水账"。**

**你可能原来是这样理解的：**

> 数据库是一个文件 —— 就像 SQLite 那样，一个 `.db` 装下所有东西。多个库就是多个文件。

**这个理解错在哪？** 一数 `base\` 下面有多少目录就知道 —— 那是**每个库一个目录**，
不是"一个库一个文件"。而 `pg_wal` 那条共享流水账，**不属于任何单个库**。

**学完你能做出什么：** 指着数据目录说出每个东西是干什么的，并知道哪几个文件绝对不能删。

## 三、观察现象和解释

### 先自己想一下：那三个多出来的目录是谁？

**答案是 —— 系统自带的库，它们的 OID 是固定的小数字。**

| `base\` 下的目录 | 是哪个库 | 说明 |
|---|---|---|
| `1` | `template1` | 建库时的模板，**OID 固定为 1** |
| `4` | `template0` | "原封不动的模板"，OID 固定为 4 |
| `5` | `postgres` | 默认库，OID 固定为 5 |
| `16389` | 你建的库之一 | **OID 从 16384 之后开始分配** |
| `16390` | 你建的另一个库 | 同上 |

**关键：目录名是 OID，不是库名。**

> 磁盘上**没法靠目录名认出哪个是哪个库**。
> 想知道 `16389` 是谁，**只能连上去查 `pg_database`**。

**去不同库各跑一次 `SELECT oid FROM pg_database` —— 结果一样吗？**

**一样。** 又是 Day 3 那个道理：`pg_database` 是**服务器级**目录，从哪个库看都一样。

### 常见误解 → 更正

| 大多数人会以为 | 其实是 |
|---|---|
| "一个库 = 一个文件" | **一个库 = 一个目录**，里面一堆文件（表、索引、系统目录…） |
| "库名就是文件夹名" | 文件夹名是 **OID**（数字）；库名只存在数据库内部 |
| "我的数据和系统数据是分开的" | 每个库目录里**既有你的表，也有那个库的系统目录**，混在一起 |
| "`pg_wal` 是我这个库的一部分" | `pg_wal` 是**服务器级**的，所有库共用，不属于任何一个库 |
| "服务停了数据就没了" | 数据在磁盘上，**服务只是个进程** —— 停不停都不影响文件 |

### `postmaster.pid` 那个坑（这台机器上真实存在）

```powershell
Get-Content -LiteralPath "$DATA\postmaster.pid"
```

**真实内容：**

```
44096
G:/Project/PostgreSQL_pocket/pgdata
1789892032
5432

localhost

ready   
```

| 行 | 意思 |
|---|---|
| `44096` | 启动时那个进程的 PID |
| `G:/.../pgdata` | 数据目录 |
| `1789892032` | 启动时间戳 |
| `5432` | 端口 |
| `localhost` | 监听地址 |

**但服务其实已经停了**（`pg_ctl status` 退出码 3）—— 这个文件是**陈旧的**。

**后果**：`pg_ctl status` 说"没在运行"，`pg_ctl start` 却说：

```
pg_ctl: another server might be running; trying to start server anyway
```

**两个命令说法不一致时，先怀疑这个文件。**

**正确处理**：确认服务真的没跑（`status` 退出码 3），再删掉 `postmaster.pid`。
**不要一看到警告就删** —— 万一服务真在跑，删了会引发更多混乱。

## 四、解释原理

### （一）它怎么工作

**哪些是"你的数据"，哪些是"机器的零件"：**

| 东西 | 是什么 | 能删吗 |
|---|---|---|
| `base\` | **每个库的数据**（一个 OID 一个目录） | ❌ 删了库就没了 |
| `global\` | 服务器级对象（比如角色） | ❌ |
| `pg_wal\` | **预写日志** —— 崩溃恢复的安全网 | ❌ 删了库起不来 |
| `pg_xact\` | 事务的提交状态 | ❌ |
| `pg_hba.conf` | 谁能连、怎么认证 | ⚠️ 能改（先备份），改错谁都连不上 |
| `postgresql.conf` | 主配置 | ⚠️ 能改，改错起不来 |
| `postgresql.auto.conf` | **用 SQL 改配置时写到这里** | ⚠️ 别手改，让 SQL 改 |
| `PG_VERSION` | 这里是哪个大版本 | ❌ |
| `postmaster.pid` | 正在运行的进程信息 | ⚠️ **只在确认没跑时删** |
| `server.log` | 日志 | ✅ 能删（这是我们自己的，不是 PostgreSQL 要的） |

**`postgresql.auto.conf` 是个隐藏彩蛋**：以后用 `ALTER SYSTEM SET ...` 改配置，
PostgreSQL **不会改 `postgresql.conf`**，而是把新值写进 `postgresql.auto.conf`。
启动时两个都读，**`auto` 优先级更高**。

**这就是"改了配置怎么没生效"有时找不到原因的地方** —— 你看的是 `postgresql.conf`，
真正生效的值在另一个文件里。

**每样东西讲三层：**

| 操作 | 谁处理 | 出错时谁报错 | 怎么反推 |
|---|---|---|---|
| `Get-ChildItem` 看目录 | **Windows** | Windows | 路径错、权限不够 —— 和数据库无关 |
| `SELECT oid FROM pg_database` | 服务器 | 服务器 | 服务没启动 → `Connection refused` |
| `pg_ctl start/stop` | **`pg_ctl` 工具** | `pg_ctl` | 它自己报，比如 `another server might be running` |

**注意最后一行**：`pg_ctl` 既不是 `psql`，也不是数据库本身 —— 它是个**独立的客户端工具**，
负责启停那个进程。所以它的报错格式和前两者又不一样。

### （二）为什么这样设计

```
存在的问题
  数据库要保证：就算突然断电，已经提交的数据也不能丢
        ↓
为什么"直接写数据文件"不够用
  一条 INSERT 可能改好几个位置：表文件、好几个索引、系统目录…
  如果写完第一个文件就断电，剩下的没写完 → 数据自相矛盾
  而且每次改一点就随机写磁盘，太慢
        ↓
这个设计解决了什么（WAL = Write-Ahead Log，预写日志）
  规则只有一条：改数据之前，先把"我要改什么"写进日志并落盘
  · 日志是顺序追加写 → 快
  · 崩了以后，重放日志就能恢复到一致状态 → 安全
  · 日志是服务器级的，所有库共用 → 只有一条账
        ↓
它带来了什么新代价
  · 磁盘占用变多（日志 + 数据两份）
  · 写入要"先日志、后数据"，多一次 I/O
  · 日志会一直长，需要 checkpoint 和清理机制
```

**一句话记住**：**先记账，再动钱。** 账本（WAL）比钱（数据文件）先落笔。

### （三）好处和代价

| 用数据目录 + WAL，好处是什么 | 代价是什么 |
|---|---|
| 断电也不丢已提交的数据 | 磁盘占用更大 |
| 备份能做到"某个时间点" | 运维变复杂：要管 checkpoint、日志保留 |
| 一个文件夹 = 一份完整数据库，搬走就能搬库 | 文件夹很大，且**不能只搬一半** —— 少一个文件就可能起不来 |
| 目录结构可见、可理解 | 但目录名是 OID，**肉眼认不出哪个库是哪个** |

**什么条件下该换别的做法：** 如果只是单机小工具、数据量小、不在乎崩溃恢复，
**SQLite 那种单文件数据库反而更合适** —— 没有服务要管、没有 WAL 要清、拷一个文件就是备份。
**PostgreSQL 的复杂度，是为"多用户并发 + 不丢数据"付的钱。**

## 五、提炼判断规律

**判断规则（要有顺序）：**

```
发现数据库起不来 / 数据不见了
  ↓
第一步：数据目录还在不在？
        不在 → 找回来或从备份恢复，别的都不用查
  ↓
第二步：pg_ctl status 说什么？
        退出码 3（没跑）但 pg_ctl start 说 "another server might be running"
        → 是 postmaster.pid 陈旧，确认没跑之后删掉它
  ↓
第三步：看 server.log 最后几行
        它通常直接说了原因（端口被占、配置写错、权限不够）
  ↓
第四步：以上都好，但连不上？
        → 回到 Day 2/3 那套判断（Connection refused / 名字 / 权限）
```

**支撑它的对照表：**

| 现象 | 谁报的 | 问题在哪 | 先查什么 |
|---|---|---|---|
| 数据目录打不开 | Windows | **和数据库无关** | 路径、权限 |
| `another server might be running` | `pg_ctl` | 启动工具的判断 | `postmaster.pid` 是否陈旧 |
| `could not create any TCP/IP sockets` | 服务器（写进日志） | 端口被占 | 换端口或找占用者 |
| 服务起得来但连不上 | `psql` | 网络 / 认证 | 回到 Day 2 的判断 |

**边界：** 这套判断**只在数据目录完整的前提下成立**。
一旦目录被删或被改坏，任何"排查"都是白费 ——
**所以第一件事永远是先确认目录还在。**

### 总结、回顾

**今天学了什么：**

数据目录就是数据库的全部家当。`base\` 里一个数字目录 = 一个库，**目录名是 OID 不是库名**。
`pg_wal\` 是所有库共用的"流水账"，用来崩溃后恢复。
配置文件是**磁盘上的普通文本文件**，服务只在启动那一刻读它们。
还发现一个真实的坑：`postmaster.pid` 可能是陈旧的，让两个命令说法不一致。

**和前面什么关系：**

Day 3 说"角色是服务器级的" —— 今天看到 `global\` 就是它在磁盘上的家，
而 `pg_database` 那种全局目录也是服务器级共享的。

### 心智模型

> **数据库 = 磁盘上一个文件夹 + 一个正在运行的进程。
> 文件夹里：`base\` 下一个 OID 目录装一个库的全部内容；`global\` 装服务器级的东西；
> `pg_wal\` 是所有库共用的一条流水账，用来崩溃恢复。
> 配置文件就是文件夹里的普通文本，只在启动时读一次。
> 文件在，数据就在 —— 进程停不停不影响。**
