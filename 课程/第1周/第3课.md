# 第 3 课：服务器、角色和数据库

> **本课对应**：`README.md` 第 1 周 Day 3
> **前置**：`课程/第1周/第2课.md`（报错判断模型）
> **状态**：✅ 已完成
> **读完本课能做出什么**：用你自己的账号干活，并且能说清"账号"和"库"是什么关系
> **本课产出的长期文件**：无

**本课的点**

- **重点**：`CREATE ROLE` / `CREATE DATABASE`；用新身份连上自己的库
- **难点**：新账号能看到、甚至能连进**不是它的**库
- **普通点**：`\du` / `\conninfo` 的用法

**今天唯一要形成的模型：**

> **PostgreSQL 是一个服务器。服务器上有两个平等的东西 —— 角色和数据库。
> 角色是"整个服务器的身份"，数据库是"独立的数据空间"。两者互不隶属。**

---

## 一、今天解决什么问题

**到今天为止，你所有操作都是用 `postgres` 这个超级用户做的。**

超管干活的麻烦很具体：你哪天手抖敲错一个 `DROP DATABASE`，**没有任何东西拦你**。
以后接真实项目，程序更不能连超管 —— 一个 SQL 注入就能删库。

**今天学的就是这个 —— 它叫角色（`ROLE`）和数据库（`DATABASE`）。**

**一句话说：角色是"一个能登录的账号"，数据库是"一个专门放数据的抽屉"。今天给自己造一套。**

**你可能原来是这样理解的：**

> 用户是属于某个数据库的 —— 我给 `learn_sql` 这个库建个用户，这个用户就归这个库管。

**这个理解错在哪？** 如果它成立，那 `learn_user` 就应该**只看得见 `learn_sql`、只连得上 `learn_sql`**。
下面的实验会让你亲眼看到它不成立。

**学完你能做出什么：** 用 `learn_user` 连上 `learn_sql` 干活，并且知道那个理解为什么不对。

## 二、动手实验

### 0. 先检查环境

**服务可能是停的。** 去 `速查/PostgreSQL速查.md` 找 **A 段（开场变量）** 和 **C 段（启动）**，跑一遍。

| 检查结果 | 下一步 |
|---|---|
| `psql` 打印出版本号 | 继续下面的实验 |
| 还是 `Connection refused` | 先解决它再往下 —— 别硬跳 |

### 1. 今天的最小工具箱

| 命令 | 干什么 | 谁处理 |
|---|---|---|
| `CREATE ROLE 名字 LOGIN PASSWORD '...'` | 建一个能登录的账号 | 服务器 |
| `CREATE DATABASE 名字 OWNER 角色` | 建一个库，指定它归谁 | 服务器 |
| `\du` | 列出所有角色 | `psql` |
| `\l` | 列出所有库 | `psql` |
| `\c 库名 用户名` | 换库**并换身份** | `psql` |
| `\conninfo` | 我现在是谁、连的哪个库 | `psql` |

**注意 `\c` 能带两个参数**：`\c 库名 用户名` —— 换库的同时换身份。

### 2. 实验 A：正常路径

**用超管连进去、建账号、建库、看一眼：**

```powershell
& "$PG\psql.exe" -U postgres -h 127.0.0.1
```

进去之后敲：

```sql
-- 建一个能登录的账号
CREATE ROLE learn_user LOGIN PASSWORD 'learn_pass';

-- 建一个库，归 learn_user 所有
CREATE DATABASE learn_sql OWNER learn_user;

-- 看角色建出来没有
\du

-- 退出
\q
```

**然后换身份，用新账号连新库，做几个动作：**

```powershell
# 用新账号连进新库，进交互界面
& "$PG\psql.exe" -U learn_user -h 127.0.0.1 -d learn_sql
```

```sql
-- 我是谁、连的哪个库
\conninfo

-- 这台服务器上有哪些库
\l

-- 换到 postgres 库（注意：那不是我的库）
\c postgres

-- 再换回来
\c learn_sql
```

### 这里应该出现两个让我"咦"的现象

**现象一：`\l` 列出了 `postgres`、`template0`、`template1`。**

```
   Name    |   Owner    | Encoding | ...
-----------+------------+----------+----
 learn_sql | learn_user | UTF8     | ...
 postgres  | postgres   | UTF8     | ...
 template0 | postgres   | UTF8     | ...
 template1 | postgres   | UTF8     | ...
```

**`learn_user` 是 `learn_sql` 的主人 —— 它凭什么看得见别人的库？**

**现象二：`\c postgres` 居然成功了。**

**你不是 `postgres` 库的主人，却能连进去。** 这说明"是不是我的"根本不影响"能不能连"。

### 3. 实验 B / C / D：三个错误，各有目的

| 实验 | 错误类型 | 它想打破的理解 |
|---|---|---|
| B | 环境错误（库名写错） | "库名写错"和"服务没启动"是同一类吗 |
| C | **权限错误（同一条命令，换个身份做）** | "**我是这个库的主人，所以我想干啥都行**" |
| D | 用户错误（读得到 ≠ 写得到） | "能看见就等于能改" |

**B —— 库名写错：**

```powershell
& "$PG\psql.exe" -U learn_user -h 127.0.0.1 -d 不存在的库 -c "SELECT 1;"
```

**C —— 同一条命令，两个身份做（这一步最重要）：**

```powershell
# C1：让 learn_user 去建一个新库
& "$PG\psql.exe" -U learn_user -h 127.0.0.1 -d learn_sql -c "CREATE DATABASE another_db;"

# C2：同一条命令，换成超管
& "$PG\psql.exe" -U postgres -h 127.0.0.1 -c "CREATE DATABASE another_db;"

# C3：让 learn_user 去建一个新角色
& "$PG\psql.exe" -U learn_user -h 127.0.0.1 -d learn_sql -c "CREATE ROLE another_user LOGIN;"

# C4：同一条命令，换成超管
& "$PG\psql.exe" -U postgres -h 127.0.0.1 -c "CREATE ROLE another_user LOGIN;"
```

**C1/C3 失败，C2/C4 成功。** 命令一模一样，**差别只有"谁在做"**。

**D —— 读和写，权限不一样：**

```powershell
# 读一张公开视图 —— 应该成功
& "$PG\psql.exe" -U learn_user -h 127.0.0.1 -d learn_sql -c "SELECT count(*) FROM pg_roles;"

# 读别人的账号表 —— 应该失败
& "$PG\psql.exe" -U learn_user -h 127.0.0.1 -d learn_sql -c "SELECT count(*) FROM pg_authid;"
```

## 三、观察现象和解释

### 先自己想一下：为什么 `learn_user` 看得见 `postgres` 库？

**答案是 —— `\l` 根本不是"当前库的内容"。**

**它是从服务器层面去查一份全局目录。** 验证方法：从 `learn_sql` 查 `pg_database` 和从 `postgres` 查，
结果**行数一样**（当时是 5 行），是同一个东西。

**把它想成图书馆：**

> 你站在 3 号书架前敲 `\l` —— 那不是"3 号书架里有什么书"，是**去门口看那本全馆总目录**。
> 总目录上当然列着 1 号、2 号、4 号书架。它们在**同一个馆里**，不是"被 3 号书架包含"。

**所以正确的是：**

> `postgres`、`template0`、`template1` **不是"`learn_sql` 里的东西"，它们是 `learn_sql` 的兄弟** —— 同属一台服务器。

### 常见误解 → 更正

| 大多数人会以为 | 其实是 |
|---|---|
| "`\l` 列出的是当前库里的东西" | `\l` 查的是**服务器级**目录，跟你在哪个库无关 |
| "用户属于某个数据库" | 用户（角色）**不属于任何数据库**，它属于服务器 |
| "不是我的库，我连不进去" | 连不连得进，和"是不是我的"**没关系** |
| "我是这个库的主人，想干啥都行" | 主人的权限**只在库内部**（建表、改表）。建库、建角色是**服务器级**动作，主人也没份 |
| "密码错了肯定连不上" | 在 `trust` 认证下，**密码根本不会被检查** |
| "能读就能写" | 权限是**逐个对象**给的，读取和写入可以是分开的两个权限 |

### 现象二：为什么能连进 `postgres` 库？

**因为"能不能连"和"是不是主人"是两回事。**

`learn_user` 能连任何库，因为 `initdb` 默认给了所有角色连接权限（`pg_hba.conf` 里是 `trust`）。

**它能连进去，但进去之后几乎什么都干不了** —— 这才是权限真正起作用的地方。

### 现象三：C3 的报错，是最好的老师

```powershell
# learn_user 建角色 → 失败
ERROR:  permission denied to create role
DETAIL:  Only roles with the CREATEROLE attribute may create roles.

# postgres 建角色 → 成功
CREATE ROLE
```

**同一条 `CREATE ROLE`，差别只在"谁在做"。**

**报错里的 `DETAIL` 那行已经把机制说出来了**：要建角色，你得有 **`CREATEROLE` 这个属性**。

> **实用判断**：报错说"需要某个属性"，那说明**问题在角色身上，不在数据库身上**。

### 现象四：`能读` ≠ `能写`

同一个 `learn_user`：

| 动作 | 结果 |
|---|---|
| `SELECT count(*) FROM pg_roles`（读公开视图） | ✅ 成功（当时 18 行） |
| `SELECT count(*) FROM pg_authid`（读别人的账号表） | ❌ `permission denied for table pg_authid` |

**同一类东西，一个能读一个不能读** —— 权限是**逐个对象**给的，不是"能看到就等于能改"。

## 四、解释原理

### （一）它怎么工作

**两个角色的真实属性对比：**

| rolname | rolsuper | rolcreatedb | rolcreaterole | rolcanlogin |
|---|---|---|---|---|
| `learn_user` | **f** | **f** | **f** | t |
| `postgres` | **t** | **t** | **t** | t |

**读到三件事：**

1. **`rolsuper = t` 是 `postgres` 唯一的本质特权。** 它的特权不是"名字叫 postgres"，是**这一列是 t**。
2. **`rolcreatedb` / `rolcreaterole` 是两个独立开关。** 不是超管也能单独给出去 —— 这就是"最小权限"的抓手。
3. **`learn_user` 只有 `rolcanlogin`**：能登录，然后什么都没有。

**所以 C1 失败的真正原因不是"它不是主人"，是它自己的 `rolcreatedb = f`。**

**每条命令讲三层：**

| 命令 | 谁处理 | 出错时谁报错 | 怎么反推 |
|---|---|---|---|
| `CREATE ROLE` / `CREATE DATABASE` | 服务器 | 服务器（`permission denied`） | 看 `DETAIL`，它说缺哪个属性 |
| `\du` / `\l` / `\c` / `\conninfo` | `psql` | `psql`（`invalid command`） | 命令没发出去，是拼写问题 |
| 连接动作本身 | `psql` 发起 | 两边都可能 | `Connection refused` = 客户端；`FATAL` = 服务器 |

### 层级关系

```
PostgreSQL 服务器（一台机器上的整套 PostgreSQL）
│
├── 角色（ROLE）              ← 服务器级，所有库共享
│    ├── postgres（超管）
│    ├── learn_user
│    └── another_user
│
├── 全局目录（pg_database、pg_roles…）   ← 服务器级，从任何库看到的都一样
│
├── 数据库 learn_sql           ← 独立空间
│    └── 表、索引、视图         ← 只有这里才是"库之间隔离"的
│
├── 数据库 postgres
│    └── 它自己的表、索引、视图  ← learn_sql 里看不见
│
└── 数据库 another_db
```

**关键一句：角色和数据库是同一层的两个平等对象，都直接挂在服务器上。**

### （二）为什么这样设计

```
存在的问题
  多个人用同一个数据库，怎么区分"谁能干什么"？
        ↓
为什么旧的做法不够用
  如果每个用户都绑死在某个库上：
    · 一个人要访问 3 个库，就得建 3 个账号 —— 密码要记 3 份
    · 权限想调整，得在 3 个地方分别改
    · 跨库操作根本做不到
        ↓
这个设计解决了什么
  角色独立于库  → 一个身份管所有库
  权限挂在角色上 → 改一处，全局生效
  库作为隔离空间 → 各库的表互不干扰
        ↓
它带来了什么新代价
  · 权限模型变复杂（服务器级权限 + 库内权限，两套要分别想）
  · 一个账号泄露，影响面是整台服务器，不只是一个库
  · 于是有了"最小权限"这套纪律：只给必需的开关
```

**生产环境为什么不用超管？** 因为 `rolsuper = t` 意味着**绕过所有权限检查** ——
上面那套"服务器级 + 库级"的模型对它完全失效。程序一旦被注入，等于把整台服务器交出去。

### （三）好处和代价

| 用角色 + 库的分离，好处是什么 | 代价是什么 |
|---|---|
| 一个身份管所有库，不用记多套账号 | 一个账号泄露，影响整台服务器 |
| 权限改一处、全局生效 | 权限分两层（服务器级 / 库内），要分别考虑 |
| 库之间表互相隔离 | 想跨库查数据，得显式指定 |

**什么条件下该换别的做法：** 如果多个库其实属于不同团队、彼此完全不该看到对方，
那就不该挤在同一台服务器上 —— **物理隔离比权限隔离更可靠**。

## 五、提炼判断规律

**判断规则（要有顺序）：**

```
看到"连不上"或"干不了"
  ↓
第一步：有没有 Connection refused？
        有 → 还没到服务器 → 查服务开没开、端口对不对
  ↓
第二步：有没有 "角色/数据库 ... 不存在"？
        有 → 已经到服务器了 → 是名字写错
  ↓
第三步：有没有 "permission denied"？
        有 → 身份对、名字对，是"没这个权限"
             → 去看报错的 DETAIL：它通常直接说需要哪个属性
  ↓
第四步：有没有 "already exists"？
        有 → 服务器在告诉你"对象已存在"，不是语法错
```

**支撑它的对照表：**

| 现象 | 谁报的 | 到哪一层了 | 先查什么 |
|---|---|---|---|
| `Connection refused` | `psql` | ❌ 没到服务器 | 服务、`-h`、`-p` |
| `FATAL: 角色 ... does not exist` | 服务器 | ✅ 到了 | `-U` |
| `FATAL: 数据库 ... does not exist` | 服务器 | ✅ 到了 | `-d` |
| `ERROR: ... already exists` | 服务器 | ✅ 到了 | 名字重了，换个名字 |
| **`ERROR: permission denied to create role`** | 服务器 | ✅ 到了 | **角色的 `CREATEROLE` 属性** |
| **`ERROR: permission denied for table pg_authid`** | 服务器 | ✅ 到了 | **这张表没给你读权限** |

**边界：** 当报错里**既有** `Connection refused` **又有** `permission denied` 时（认证方式配错会出现），
**优先看 `Connection refused`** —— 连都没连上，后面的权限根本谈不上。

### 总结、回顾

**今天学了什么：**

用 `CREATE ROLE` 建账号、`CREATE DATABASE` 建库，用新身份连上自己的库。
更重要的是：**角色和数据库是服务器上两个平等的对象** —— 角色不属于任何库，库也管不到角色。
`\l` 能看到所有库，是因为它查的是**服务器级目录**，跟你在哪个库无关。

**和前面什么关系：**

Day 2 教了怎么判断"报错在哪一层"；今天这一层多了一个新的可能：**权限**。
报错从"名字不对"扩展到"名字对、身份对，但没有这个权限"。

### 心智模型

> **PostgreSQL 是一台服务器。服务器上挂着两样平等的东西 —— 角色（身份）和数据库（空间）。
> 角色全服务器共享；数据库之间靠"表在哪个库里"来隔离。
> 权限分两层：服务器级（建库、建角色）挂在角色的属性上；库内级（建表、查表）挂在库和对象上。**
